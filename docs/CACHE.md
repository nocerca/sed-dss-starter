# Кэш повторных тяжёлых проверок

В v0.6 кэш включён для запросов с `use_llm=true` или `use_language_checks=true`. Он повторно выдаёт существующий успешный отчёт при совпадении байтов файла и параметров. Первый запуск не ускоряет. Быстрые проверки только правилами не кэшируются.

## Почему это целесообразно

При просмотре 75 локальных сохранённых отчётов у 59 были тайминги: медиана total_before_final_save_ms — 144,6 мс, медиана parse_ms — 128,56 мс. У пяти был этап шлюза, максимальный llm_gateway_ms — 102 759,9 мс. У 14 был языковой этап, медиана — 353,23 мс, максимум — 8036,31 мс. Это смесь отдельных запусков, включая синтетические проверки и сбои, а не репрезентативный бенчмарк или обещание задержки. Основной выигрыш ожидается при повторении успешного вызова модели; разбор и правила для обычного письма уже занимают доли секунды.

Redis для одного процесса API не добавлен. Кэш содержит только непрозрачный HMAC-ключ, ID сохранённого отчёта и срок действия. Файл, извлечённый текст, замечания и история шлюза в нём не дублируются. Повторное использование не продлевает срок хранения отчёта в БД.

Контрольный REST-прогон на одном синтетическом DOCX с локальным LanguageTool: miss — 475,91 мс, hit — 16,90 мс, обход — 445,20 мс по клиентскому таймеру. Hit вернул прежний ID, обход создал новый. Это один замер, не обещание ускорения для любого файла; внешняя модель не вызывалась. Отдельная сквозная проверка с настоящим изолированным OpenClaw и тестовой моделью подтвердила hit без нового вызова шлюза.

## Как пользоваться

Поле формы `use_cache=true` задано по умолчанию. В ответе смотрите заголовок `Analysis-Cache`:

| Значение | Значение для запроса |
|---|---|
| `miss` | Подходящего успешного отчёта нет; выполняется новый тяжёлый анализ |
| `hit` | Выдан прежний отчёт; модель и LanguageTool повторно не вызывались |
| `bypass` | Кэш явно обойдён, выключен, заполнен активными ключами, запрос только с правилами либо это идемпотентный повтор |
| `busy` | HTTP 409 и Retry-After=2: в этом процессе уже выполняется такой тяжёлый анализ; второй запуск не начат |

При hit возвращаются прежние `id`, `created_at`, `request_id` и метрики времени первоначального анализа. Текущую длительность HTTP показывает `Server-Timing`, текущий запрос — заголовок `X-Request-ID`. Нового отчёта в БД нет. Если был передан новый Idempotency-Key, он связывается с этим отчётом.

Для нового расчёта задайте `use_cache=false` и используйте новый Idempotency-Key либо уберите этот заголовок. False обходит и чтение, и запись кэша для одного запроса; существующая запись остаётся до истечения TTL/вытеснения. Со старым ключом идемпотентности возвращается старый результат или 409 при изменении параметров, даже если хочется нового расчёта.

В Postman папка **07 — Кэш тяжёлых проверок без внешней модели** содержит три запроса: обычный запуск LanguageTool, повтор с ожиданием hit и расчёт с use_cache=false. Выбирайте один и тот же файл, сохраняйте все поля; нужен запущенный локальный LanguageTool. Для модели согласие external_consent=true по-прежнему требуется перед каждым Send, даже если ожидается hit.

## Настройки

```dotenv
ANALYSIS_CACHE_ENABLED=true
ANALYSIS_CACHE_TTL_SECONDS=900
ANALYSIS_CACHE_MAX_ENTRIES=128
```

Настройки доступны в `/api/v1/capabilities`. Применяются после пересоздания API. По умолчанию — 15 минут, до 128 завершённых записей и до 128 активных ключей. Завершённые записи вытесняются по LRU; истёкшие метаданные удаляются при обращении к кэшу. Перезапуск очищает всё состояние; долговременная идемпотентность в PostgreSQL сохраняется. Дополнительных зависимостей и миграций нет.

## Инвалидация и приватность

Ключ учитывает файл, имя, внешний ID, тип/шаблон/профиль письма, флаги анализа/согласия, версию приложения, полную спецификацию и включённость правил, конфигурацию языка, шлюза и идентификаторы бэкенда/моделей, содержимое и источники базы знаний. Даже пересохранение DOCX без видимых изменений может изменить ZIP-байты и дать miss.

При изменении модели, ключа провайдера или конфигурации OpenClaw пересоздавайте **API и шлюз вместе**: API получает несекретные идентификаторы моделей, но не читает секреты и внутреннюю конфигурацию шлюза. Изменения, сделанные только внутри отдельно работающего шлюза, API автоматически не видит. Пересоздание API сбрасывает кэш.

Согласие, глобальное разрешение и X-API-Key проверяются до кэша. Ключ кэша не сохраняется в БД/логах и не возвращается клиенту. Удаление отчёта через API инвалидирует ссылки и превращает все связанные ключи идемпотентности в 410. После очистки отчётов другим процессом наличие записи дополнительно проверяется в БД — удалённый отчёт не восстанавливается из кэша. Partial/processing и исключения не кэшируются.

Это кэш одного процесса, не распределённая блокировка между репликами и не гарантия однократного исполнения провайдером после аварии. Для повтора одной операции сохраняйте исходный Idempotency-Key. Все приватные REST-ответы получают `Cache-Control: no-store`; браузеру/прокси не предлагается хранить документы.

Для независимых исследовательских замеров задавайте use_cache=false и новые ключи: сохранённые тайминги при hit не являются новым измерением.
