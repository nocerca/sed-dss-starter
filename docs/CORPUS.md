# Корпус писем и правила разметки

## Полученные материалы

На 01.11.2026 локально получено 41 письмо и инструкция по делопроизводству. Письма имеют статус `unreviewed`: сотрудник предупредил о возможных исходных ошибках. Инструкция разобрана в отдельный [профиль требований](LETTER_POLICY.md); нормативный источник не смешивается с примерами.

04.11.2026 все 41 письмо разобраны локально реализованными проверками профиля; ошибок разбора не было, исходные хеши совпали. Предварительные замечания сохранены в `examples/private/policy/preliminary_checks.json` без экспертных меток и без внешней передачи. Это материал для обсуждения с сотрудником, не оценка точности. Десять демонстрационных дефектов и два контроля генерируются отдельно из полностью синтетического письма, исходные частные тексты не используются.

Локальные пути/хеши и статусы сохранены в `examples/private/policy/letters_inventory.json`; привязка требований к конкретной копии инструкции — в `source_binding.json` рядом. Оба файла исключены из Git и Docker. Автоматической загрузки в БД или передачи модели нет. Факт получения файлов не подтверждает их обезличивание и разрешение внешней обработки.

## Что запросить
Желательно 20–40 **обезличенных** исходящих служебных писем в DOCX (по возможности с исходным форматированием), разных типов: запрос, ответ, уведомление, сопроводительное письмо. Помимо корректных образцов нужны заведомо проблемные, но с **подтверждением конкретных ошибок** и экспертным правильным вариантом.

Отдельно запросить применимые корпоративные шаблоны, инструкции по делопроизводству, требования к реквизитам, типографике и стиле. Не путать их с корпусом писем. Разрешение на учебную обработку и передачу во внешние сервисы — **разные согласия**.

## Метаданные и разметка
Планируемый CSV/JSONL для каждого документа:

| Поле | Содержание |
|---|---|
| doc_id | обезличенный идентификатор |
| file_name | путь/имя в защищённом хранилище |
| doc_type | запрос, ответ, уведомление, сопроводительное |
| role | normative / good / bad / evaluation |
| approval | разрешён для локальной обработки? внешнего API? |
| source_ref | реквизиты нормативного источника или экспертной разметки |
| rule_version | применимая версия требования |
| defect_spans | список точных фрагментов текста |
| defect_category | language / content / formatting |
| defect_type | конкретный код ошибки |
| severity | info / warning / critical |
| explanation | почему это недостаток |
| suggested_fix | предлагаемая правка, если есть |
| annotator | код эксперта, без ФИО |
| confidence | согласие экспертов/неоднозначность |
| split | knowledge / validation / test |

**Важно:** недостаток может быть в структуре или формате, поэтому одних текстовых цитат недостаточно. Для таких дефектов добавлять селекторы OOXML/адрес абзаца/поле карточки.

## Перед использованием
1. Убрать ФИО, телефоны, адреса, служебные номера, персональные и коммерческие сведения.
2. Согласовать с научруком правомерность сохранения в локальной БД и отправки внешнему провайдеру.
3. Разделить источники правил, положительные/отрицательные примеры и независимые тесты.
4. Эксперты размечают категорию, доказательство, необходимость исправления и допустимые варианты.
5. Зафиксировать версии корпуса и инструкции для воспроизводимости эксперимента.

До экспертной разметки и разделения выборок измерения качества остаются отложенными. Производные копии с контролируемыми дефектами не являются независимыми письмами: все варианты одного исходника должны попадать в одну группу. В разметке различать `violation`, допустимый контрольный вариант и `needs_review`; не считать замену цифровой даты разрешённой словесной датой ошибкой. Удаление телефона исполнителя размечать только после подтверждения его роли и наличия в оригинале. Дефекты интервалов перед подписью требуют проверки реальной раскладки, а не подсчёта пустых XML-абзацев.
