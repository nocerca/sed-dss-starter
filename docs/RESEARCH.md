# Научная часть — постановка исследования, не готовые результаты

## Тема (рабочая)
Разработка гибридного метода интеллектуальной оценки качества исходящей деловой корреспонденции в системе поддержки принятия решений.

## Объект и предмет
**Объект:** процесс подготовки и проверки исходящей деловой корреспонденции в СЭД.
**Предмет:** алгоритмы объединения формальных правил, нормативно-методических знаний, примеров документов и выводов языковых моделей для обнаружения недостатков.

## Цель
Разработать и исследовать метод, позволяющий формировать проверяемые и объяснимые замечания к исходящим служебным письмам.

## Гипотеза (требует проверки)
Совместная обработка формализованных правил, извлечённых знаний и LLM с проверкой источников уменьшит число ложных замечаний и/или повысит полноту выявления недостатков относительно отдельных подходов.

## Предполагаемый авторский вклад
Не сама интеграция модели по API, а **метод разрешения и верификации рекомендаций**, в котором для каждого замечания фиксируются: текстовое доказательство, источник, тип знания, применимость правила, конфликтующие основания и критичность. Не объявлять этот метод уникальным до обзора литературы и сравнений.

## Алгоритм (исследовательская полная версия, НЕ реализован в MVP)
1. Нормализация DOCX в структурную модель с координатами фрагментов.
2. Формальные проверки по версии правил и типу документа.
3. Извлечение применимых нормативных знаний и размеченных образцов.
4. Контекстный LLM-анализ через обязательный OpenClaw (без права подставлять факты в исправления); backend Яндекса/GigaChat/Z.AI доступны в коде. Реальный вызов Z.AI подтверждён на синтетическом письме, но экспертное качество не измерено; для Яндекса/GigaChat нужны отдельные проверки. Ollama и Llama запрещены.
5. Кросс-проверка каждого замечания: ссылка существует; правило применимо; фрагмент найден; степень риска известна.
6. Дедупликация и согласование конфликтов; вывод мотивированной рекомендации.

## Экспериментальные группы (ablation study)
A. Только формальные правила.
B. Только LLM.
C. LLM + retrieval.
D. Гибридный метод (правила + retrieval + верификация).

В группах B/C/D обращения к модели должны проходить через OpenClaw с одинаковой конфигурацией ограничений; группа A не обращается к модели. Обязательность OpenClaw — архитектурное требование пользователя, а не доказательство научной новизны или улучшения качества.

При будущем сравнении также фиксировать `use_language_checks`, версию LanguageTool, фильтр допуска, версию структурного контекста и флаги жанровых предупреждений. Сейчас эти механизмы проверены синтетическими тестами; уменьшение ложных срабатываний на реальном корпусе и ускорение анализа не измерены.

Начиная с v0.6 для независимых временных измерений задавать use_cache=false и новый Idempotency-Key (или не передавать ключ). При Analysis-Cache=hit возвращаются исторические тайминги исходного отчёта; такой ответ не является новым измерением модели. Кэш полезен для повторов в эксплуатации, но его попадания нельзя выдавать за ускорение первого модельного анализа.

Получено 41 исходное письмо без подтверждённой разметки. По отдельному источнику подготовлен [каталог требований](LETTER_POLICY.md); в v0.5 реализована часть проверок явно выбранного профиля. Предварительный локальный прогон оригиналов и проверки десяти искусственных дефектов/двух контролей подтверждают технические сценарии, не экспертную точность. Производные одного письма должны оставаться в одной группе, чтобы не допустить утечки между базой примеров и тестами.

## Метрики результата
- Precision = TP/(TP+FP), Recall = TP/(TP+FN), F1 = 2PR/(P+R).
- Среднее число ложноположительных замечаний на письмо.
- Покрытие дефектов по категориям: язык, содержание, оформление.
- Доля замечаний с проверяемым источником, доля отклонённых ложных ссылок.
- Затраты времени и, при доступности, стоимость API на документ.
- Согласованность экспертов в разметке (например, Cohen κ для двух независимых экспертов); пользовательская оценка полезности рекомендаций — отдельно.

**Важно:** 20–40 документов для базы знаний ≠ независимая тестовая выборка. Не использовать один и тот же набор одновременно как примеры и как тест без разделения; для разреженных классов ошибок нужны дополнительно размеченные документы. Не публиковать придуманные результаты и значения метрик.

## Метрики качества одного письма
Держать независимые количественные оценки (счётчики нарушений/доли выполненных применимых правил) по категориям. Общая оценка не входит в MVP, пока не обоснованы веса и критические ограничения. Классификация `info/warning/critical` предварительная.
